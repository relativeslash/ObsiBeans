# ObsiBeans AI working guide

Canonical AI workflow entry point for this repository. Start with [[docs/Private/Contributing/Standards/README.md|shared standards]], then [[docs/Private/Contributing/README.md|ObsiBeans contributing guidance]] and [[docs/Private/Contributing/ObsiBeans project info.md|project information and compatibility baseline]].

Local standards notes are optional overrides, not a required parallel set of global standards. Their absence or empty content does not block work; inherit the shared rules. Follow the contributing entry point for the distinction between optional overrides and genuinely required guidance.

## Skills and local workflow

Load `protomatter-workspace` at session start and work in the epic clone it sets up, never in the primary checkout. Then load `protomatter-repo-navigation` and the task-relevant skills: `beans` for work tracking, `obsidian-cli` for live vault operations, and `obsidian-markdown` for note syntax.

The repository root is the `ObsiBeans` vault. Retain `docs/` in vault-relative documentation paths and explicitly target that vault.

Use the Beans skill to search for an existing task before creating work records and to keep them current. Read `.beans.yml` for tracking configuration rather than assuming a task directory or ID prefix. Keep design decisions in [[docs/Private/Design/ObsiBeans native workspace proposal.md|design documentation]] and link them from work records.

## Plugin development

A plugin skeleton with quality gates exists: a workspace view, an open command and a settings tab, without Beans features. [[docs/Private/Contributing/ObsiBeans project info.md|Project information]] owns the toolchain pins, source layout, module boundaries and verified commands. Run `yarn install --immutable` once, then `yarn verify` before handing off any code change; it is what CI runs.

- Yarn uses Plug'n'Play, so there is no `node_modules`. Run Node scripts through Yarn (`yarn node file.ts` or a package script); plain `node` cannot resolve packages. Editors need Plug'n'Play support or Yarn's editor SDK.
- Put new production code under the layer directory that owns it. `yarn fitness` rejects files outside a layer, forbidden imports and import cycles. Change the rules only together with the design note's module boundaries.
- Route every UI string through `t()` with a new key in `src/views/messages.en.ts`. Never pass inline prose.
- Obsidian 1.14 renders settings from `getSettingDefinitions()`. `PluginSettingTab.display()` is deprecated, and lint rejects deprecated APIs.
- Headless tests get `obsidian` from `test/support/obsidian.ts`. Extend that stub only with API that production code uses. Use `bridge()` to cross between stub and real types instead of double assertions. Add `// @vitest-environment jsdom` to tests that render.
- `yarn typecheck` runs svelte-check, which checks both `.ts` and `.svelte` files and fails on Svelte accessibility warnings.
- The stub cannot prove real Obsidian behavior. After changing lifecycle, commands, views or settings, run `yarn test:native`. It needs a desktop session and runs a separate Obsidian instance, so the user's vaults are untouched.

## Beans backend

Before writing adapter, state, or view code, read [[docs/Private/Design/Beans 0.4.2 contract.md|the Beans 0.4.2 contract]]. The plugin depends on several non-obvious behaviors recorded there: queried ETags can be rejected, updates drop unknown frontmatter, GraphQL validates no field values, and blocking links are stored in two directions. For view and keyboard work, also read [[docs/Private/Design/Beans 0.4.2 TUI parity matrix.md|the TUI parity matrix]]. Never run experiments against this repository's own tracker; the audit script shows how to use a temporary project.

Typed reads and writes live next to it. `listBeans`, `getBean`, `createBean` and `mutateBean` take a `BeansContext` (runner, binding, `parseYaml`) and return an `Outcome` with a distinct `validation`, `conflict`, `preservation`, `backend` or `uncertain` error. A read gives each bean a `revision`, the hash of its file bytes; pass it back to `mutateBean` as the basis of one change, because Beans' own queried ETag is rejected for non-canonical files. Never retry after `uncertain` until the caller has compared `current` (or, for creation, `createdIds`) with its intent. Creation has no ETag guard in Beans. Add an adapter test against a scripted Beans (`writeScriptedBeans` in `test/support/project.ts`) and, for behavior that touches Beans itself, a case in `test/adapter/beans-adapter-release.test.ts`.

Process and project binding live in `src/adapter/`: the plugin shell constructs one `ProcessRunner` and passes it to `bindProject`, `runBeans` and `scanTaskRoot`. Never call `child_process` elsewhere. Adapter tests use Node scripts as fake executables (`test/support/project.ts`) and need no Beans install; the release-binary tests need `OBSIBEANS_BEANS_RELEASE`, described in [[docs/Private/Contributing/ObsiBeans project info.md|project information]]. The plugin supports Beans 0.4.2 and also accepts a development build (reports `dev`), marked unverified; any other version is rejected. The executable must live outside the vault. The user trusts an executable explicitly in settings; trust is the file's real path plus a SHA-256 of its content, so replacing the file withdraws it.

## Shared state

Views and commands read and change the project only through `WorkspaceState` (`src/state/workspace-state.ts`); no view calls the adapter. The plugin shell owns one per verified binding (`plugin.state`, `undefined` while unbound or checking) and replaces it on every rebind, so follow `onBindingChange` and re-read `plugin.state`. Never hold on to an old instance: a disposed state ignores every call and never notifies again.

**Reading.** `getSnapshot()` returns an immutable `Snapshot`, a new object after every change and the same one otherwise; `subscribe(listener)` returns the stop function. `status` is one of `loading`, `empty` (no beans), `no-matches` (filters hide everything), `ready`, `disconnected` or `invalid-data`; the last two appear only while nothing is cached. When a refresh fails with data cached, `status` stays data-based, `failure` holds the error and `stale` is true next to `refreshedAt`, so show a banner over the old rows. `refreshing` is a load in flight. `saves` maps a bean ID (or `new:<localKey>` for a creation) to `pending`, `failed`, `conflict` or `uncertain`; absence means saved. `beans` and `visible` are in one deterministic order (status, priority, type, title, ID), so rows do not jump between refreshes.

**Acting.** `setFilters(patch)`, `select(id)` (the inspector's bean; `selectedGone` says it vanished), `toggleSelected`, `setSelected`, `selectVisible`, `clearSelection` (selection is a separate explicit set that survives filters; `selection.hidden` counts hidden members, and only existing beans can join it), `dismissNotice`, `refresh()` (explicit, immediate, replaces a load in flight). `setViewState(view, { scrollTop, focusId })` and `getViewState(view)` remember scroll and focus per view and deliberately do not notify.

**Writing.** `mutate(id, change, basis?)` and `create(localKey, bean)` return `saved`, `failed` (carrying the adapter's `AdapterError`) or `ignored`. The cached bean changes only after Beans confirms; render a `pending` save as an intention, never as data. A second call for a key that is `pending` is `ignored: busy`, so disable the control and show the pending state anyway. After `uncertain` the key refuses writes (`ignored: unreconciled`) until `dismissSave(key)`, because a retry could duplicate the write; compare `error.current` (or `error.createdIds`) with the intent first. After a `conflict`, review `error.current` and either discard the draft or call `mutate` again with `basis` set to `error.current.revision` as an explicit overwrite. `basis` defaults to the cached revision; an editor passes the revision it started from. Bulk work is one `mutate` per bean with a concurrency limit chosen by the caller.

**Refreshing.** The shell routes vault `create`, `modify`, `delete` and `rename` events under the bound task root to `vaultChanged(path, oldPath?)`, which coalesces bursts into one load after 300 ms of quiet. Obsidian does not index dot-files, so it reports no events for `.beans.yml` (observed in the native smoke test); every load instead first compares the config file's content with the binding (`configUnchanged`) and rebinds when it differs, so a config change is noticed at the next load or Refresh command, not at once. Only the newest load counts: older answers are aborted and ignored, and a confirmed write supersedes loads in flight. A failed parse is retried once after the debounce.

**Drafts.** Unsaved description text and creation forms are `Draft`s (`kind`, `key`, `text`, `revision`, `savedAt`): the key is the full bean ID, or the form's local key for a creation, and `revision` is the bean revision the edit started from (Beans' own ETag is not used). Call `setDraft` while the user types; it is written after 400 ms of quiet and flushed when the state is disposed. A `body` change that fails keeps its text as a draft by itself, and a successful save or `discardDraft` removes it. `snapshot.drafts` lists each with a status: `current`, `changed` (the bean changed since; restore needs conflict review), `orphaned` (the bean no longer exists; the text stays listed so it can be copied) or `unchecked` (not loaded yet). `restoreDraft(kind, key)` returns what to do and never overwrites anything. The list is stored with the settings in the plugin's `data.json` under `drafts`; the shell writes both through one serialized `persist()`, so neither erases the other. `draftsUnsaved` is true while storage failed. A creation form serializes its fields into `text`; the format is the form's to choose.

**Testing with it.** `test/state/support.ts` has `FakePort` (every call waits until the test settles it, so out-of-order answers are easy to stage), `bean`, `detail`, `read`, `harness` and `loaded`; use `vi.useFakeTimers()` for debounce. `test/plugin/state.test.ts` binds the plugin to a scripted Beans and drives the stub's `vault.trigger` events; `test/native/smoke.ts` does the same with real files in a real Obsidian.

## Views

Two `ItemView`s (`src/views/workspace-view.ts`) share one Svelte lifecycle: `WorkspaceView` (navigation, list, inspector, status bar) and `IssueView` (one bean per tab, identified by its full ID; `plugin.openIssue(id)` reveals an open tab instead of duplicating it). Views receive a `WorkspaceHost` (`host.ts`), never the plugin; the plugin implements it. Call `follow(host)` (`follow.svelte.ts`) in a component to get the current `state`, its `snapshot` and the binding text as reactive values; it re-attaches on every rebind. Name a local `project`, not `state`: Svelte reads `$state` as a store of `state`.

- Built-in navigation entries are fixed filter sets in `src/state/navigation.ts` (`navFilters`); choosing one replaces all filters, so the entry is what the list shows. Readiness always uses the backend's meaning.
- Saved layout (navigation entry, inspector width) lives in the view's `getState`/`setState`, so Obsidian stores it with the workspace layout; `setState` remounts the component. Density is a plugin setting and reaches views through the host.
- Below 760 px the panes stack (views, list, details with Back). The list stays mounted but hidden and puts its scroll position and focused row back from `WorkspaceState.setViewState` when it returns.
- The list (`WorkList.svelte` rows, `ListControls.svelte` search, chips, sort, columns, selection bar and copy) draws `listRows(...)` from `src/state/filters.ts`: the matches plus every ancestor of a match as a `context` row. Context rows are drawn dimmed and labelled, have no checkbox or pickers, and are never in `snapshot.visible`, the match count, `selectVisible` or the copied IDs. Sorting is client-side (`sortBeans`), stable, and ties keep the default order ending in the full ID. Sort and column choices are part of the saved `Layout`; filters are not (the navigation entry is).
- Inline status/type/priority pickers call `project.mutate` and show a `pending` save as the asked-for value. After any result the picker is reset to the cached value, so a failed save never leaves the wrong value on screen. After a conflict the row offers to apply the same change again on top of the current revision.
- List shortcuts (`j`/`k`, Space to select and advance, `y` copy, `/` search, `g t` tags, Escape) are handled once on the list pane and ignored inside text fields; each also has a visible control. Rows use `content-visibility: auto` instead of a virtual list; 2,002 rows render in about 1.5 s in the native smoke test.
- Key keyed `{#each}` blocks by something unique per file: two files can claim one ID, and a duplicate key stops the whole component tree from updating (found in the native smoke test).
- The inspector (`Inspector.svelte`) takes the `WorkspaceHost` and the `WorkspaceState`. It composes `Fields.svelte` (title, status, type, priority and tags, each saved on its own with feedback beside the field), `Description.svelte` (rendered description, checklist, Save/Cancel editor, draft restore and conflict review) and `SaveFeedback.svelte` (the one rendering of a `pending`, `failed`, `conflict` or `uncertain` save). Inspector, issue tab and dedicated tabs share these components, so behavior is identical. Components are keyed by bean ID; save state is per bean, so a component shows a result only when it started the write (`mine`).
- The description is not part of a list row. `WorkspaceState.detail(id)` reads one bean with its body through the port (`BeansPort.get`); `Description` re-reads whenever the bean's revision changes and ignores an older answer. Editors use `bodyText` (`src/state/body.ts`), which drops the one leading and one trailing newline Beans adds or removes, and an edit's basis is the revision of the read it started from. `checklistItems` yields the items with the exact line of the body as read; the adapter targets that line, so repeated item texts stay distinct, and lines inside fenced code are skipped.
- Markdown is drawn by Obsidian's renderer through `WorkspaceHost.renderMarkdown`, never by the views, so untrusted descriptions are sanitized by Obsidian (verified in the native smoke test with an `onerror` attribute). The host makes rendered task checkboxes read-only because the checklist list is the only way to change them. `openSource` and `sourceLink` resolve the file from the path the project last listed for the full ID, so a title change never matters; the link uses the user's link style (`generateMarkdownLink`).
- Creation (`CreateForm.svelte`, `create-form.ts`) is one form under the local key `form`: its fields are serialized into the creation draft while typing, so leaving the form and coming back restores it, and Cancel discards it. An empty type, status or priority means the project default, which the adapter sends explicitly; the options show the effective defaults from `WorkspaceState.defaults`. Create draft always sends `status: draft`. Beans' creation has no guard, so after an `uncertain` result the form stays locked until the user confirms (`dismissSave`), and the IDs that appeared are listed.
- Relationships (`Parent.svelte`, `Links.svelte`, `BeanPicker.svelte`, `src/state/relations.ts`): the inspector shows the parent chain with links, a searchable eligible-parent picker with "No parent" first (`eligibleParents`: type allowed by `PARENT_TYPES`, outside the bean's own subtree; a milestone has none and says why), and separate Blocked by and Blocks lists built from both storage directions with add and remove. An add writes the bean being edited (`blocking` for Blocks, `blocked-by` for Blocked by); a removal goes through the file that stores the link (`removalPlan`), so it can write the other bean. `WorkspaceState.mutate` first runs `localProblem` for every caller: a type change that breaks the parent or a child (BC-30) and a blocking loop that mixes both directions (BC-35) are rejected there without calling Beans; everything else is left to Beans. A relationship result is shown only by the component that started it (`mine`/`involved`), keyed by bean ID like every save. `p` opens the parent picker and `b` the picker for a bean to block (TP-18, TP-19); both act on the shown bean only (TP-25). The New child button (`onNewChild`, workspace and issue tab) opens `CreateForm` with `parentId`, stored in the form draft as `parent`; Beans validates the type, and Cancel creates nothing.
- Hierarchy (`Hierarchy.svelte`, `src/state/hierarchy.ts`; the third `Layout.view` beside list and board): `hierarchyRows` turns `listRows` (matches plus ancestors as `context`) into a depth-first tree, each level in the chosen sort. A parent is open when the user chose so (`expanded`, a `Map` of full bean ID to boolean kept in `WorkList`, so view switches keep it and a refresh cannot misplace it), and otherwise open while a filter hides beans and closed when nothing is filtered, so matches are never buried under a closed parent. Under a filter only matches and their ancestors are children; context rows have a twisty but no checkbox and are never in `visible`, counts or selection. Right opens a closed parent or enters its first child, Left closes an open one or returns to the parent row; `j`/`k`/arrows/Space from the list still apply (rows are `button.row`). A bean whose parent does not exist, or that sits in a parent loop, is drawn as a top-level row with a `problem` (named parent ID, or "Parent loop") and the inspector's parent editor fixes it; every bean is drawn once whatever the data holds. Progress (`progressByBean`) is always over the whole project and counts leaf descendants at any depth, never the parent or intermediate parents (so an empty epic below a milestone is one open or finished leaf): completed and scrapped apart, percent is completed over leaves that are not scrapped (rounded down, so 100 means done), "All scrapped (n)" when only scrapped leaves remain, and "No child work" for a milestone, epic or feature without children. `blockersByBean` lists open blockers (BC-38) from both storage directions and flags a blocking loop. The row's New child button reuses `startCreating(parent)`. After any write the snapshot reloads, so tree and progress follow backend state; `test/views/hierarchy.test.ts` has the fixtures (multi-level, empty milestone, mixed leaves, filtered, missing parent, parent and blocking loops, parent change).
- Bulk editing (`BulkBar.svelte`, `BulkResults.svelte`, `src/state/bulk.ts`; TP-22 to TP-25): the bar appears over the list while anything is selected and names the explicit target count, hidden beans included, with a review list that removes single beans. One edit (status, type, priority or parent) goes to every selected bean through `WorkspaceState.applyBulk`, which hands the selection to `BulkRunner`: one `mutate` per bean, strictly one after another, each on the revision it had when the user pressed Apply. The run owns its targets, so later selection changes and refreshes do not alter it; a bean that vanished is `skipped`. Each item ends as `saved`, `unchanged` (already had the value, no write), `failed`, `conflict`, `uncertain`, `skipped` or `cancelled`, and the results panel lists every problem next to a summary that never hides partial completion. Parent edits are checked per bean in `localProblem` (type table, own parent, own subtree) before Beans is called. Cancel stops before the next bean and reports the one in flight truthfully. Retry re-reads the project first, then runs only beans without a saved result (a bean that now has the value becomes `unchanged`); an `uncertain` bean is retried only after the user checked it (`reconcileBulk`). A run stays on screen until closed, and `applyBulk` refuses to start another meanwhile. Relationship and body edits are not bulk actions (TP-25). `test/adapter/bulk-release.test.ts` drives the whole flow against a real Beans binary with a conflict, a backend loss, a write whose answer is lost and a locally refused bean, and compares each outcome with the files on disk.
- Saved views (`src/state/saved-views.ts`, `Navigation.svelte`, `host.savedViews` / `host.changeViews`; design: [[docs/Private/Design/ObsiBeans native workspace proposal.md#Saved views|Saved views]]): a saved view is the shared `Filters` plus `representation`, `sort` and `swimlanes`, stored only in the plugin's `data.json` beside the settings and drafts. The file carries `schemaVersion` (now 1); `loadViews` runs `STEPS[n]` one version at a time (add a step and bump `SCHEMA_VERSION` for a format change), reads every entry on its own, and keeps what it cannot read as an `invalid` entry holding the raw value, which `serializeViews` writes back unchanged. Data from a newer version is kept as raw `newer` entries and its version number survives. `applyViewChange` is the one pure place for save, update, rename and remove (names are unique ignoring case); `plugin.changeViews` stores the result, tells followers through `onBindingChange` and, if the write fails, restores the list and answers `storage`. `Layout.savedView` names the applied view (per workspace tab, like the rest of the layout). The active entry, built-in or saved, is the filter: `Workspace.svelte` re-applies it only when its filter values change, so renaming does not wipe filters being edited; applying a view again resets them. A view whose ID no longer exists shows a banner and falls back to the built-in entry. Values the project no longer reports (a removed status, a tag no bean has) stay in the view and are listed as "Not in the project". Usage and limits (private): Save view stores what is on screen under the name typed; the applied view offers Update, Rename and Remove (with confirmation); views are never written to a bean file or the repository and are not shared between vaults or clones, so copy `savedViews` from `data.json` by hand to move them. No saved-view action calls Beans (`test/plugin/state.test.ts`, native smoke).
- Sidebar (`Sidebar.svelte`, `SidebarView` in `workspace-view.ts`, command `Open Ready and In progress sidebar`): a compact side-pane list of the Ready and In progress beans. It follows the same `WorkspaceState` as the workspace and reads `WorkspaceState.matching(navFilters('ready' | 'in-progress'))`, so Ready is the backend's readiness, whatever filters the workspace list has. A row opens the bean in its issue tab. It shows the loading, empty, disconnected, invalid-data and stale states and the shared status bar, and refreshes with the state after vault changes or Refresh. It opens in the right split and reuses an existing leaf.
- Note links and selected-text conversion (`src/plugin/notes.ts`, `Notes.svelte`, `ConvertDialog.svelte`, `LinkDialog.svelte`, `src/state/note-text.ts`; design: [[docs/Private/Design/ObsiBeans native workspace proposal.md#Note links and selected-text conversion|Note links and selected-text conversion]]): the host's `relatedNotes(id)` reads Obsidian's `metadataCache.resolvedLinks` for the bean's file (backlinks and outgoing links) and `Notes.svelte` re-reads it on `onBindingChange`, which the shell raises when Obsidian reports `resolved`; it never parses note text itself. The commands `Insert bean link` and `Convert selection to bean` are editor commands (`editorCheckCallback`, so absent without a note, a bound project or, for conversion, a non-empty selection) and also appear in the editor context menu. A command captures a `NoteTarget`: the file, the editor and the selection with 40 characters of context on each side (`anchorAt`). `NoteTarget.insert` writes only if the same editor is still open on the same file and `locate` finds that context at its old place or at exactly one other place; otherwise it returns `changed` or `gone` and writes nothing. It only ever inserts after the selection or, on explicit choice, replaces the located selection. Conversion creates through `WorkspaceState.create('convert', …)` once; from then on only the note write can be retried, so a retry never creates a second bean, and the dialog keeps the link text (`NoteTarget.link`, which falls back to a name link while Obsidian has not indexed the new file) for copying. An `uncertain` creation locks the dialog until reconciled, like the creation form. Editors that are not a workspace leaf (canvas cards, embedded editors) report `gone`. Native smoke covers resolution, link-aware moves of a note and of a bean file (it sets `alwaysUpdateLinks`, or Obsidian waits for an answer to its "Update links?" prompt), both commands, the context menu, a concurrent edit and a retry. `test/support/obsidian.ts` has `Modal`, `MetadataCache` and `Workspace.on` for it.
- Detail keys (TP-14 and TP-22): `s`, `t` and `P` focus the pickers, `e` edits the description, `y` copies the ID; `c` in the list opens the creation form. All are ignored inside text fields.
- Headless component tests for the inspector and creation use `test/views/ui.ts` (`open`, a `TestHost` that records source actions, and `settle`) over the `FakePort` of `test/state/support.ts`; its pending `gets`, `mutations` and `creations` are answered by the test. `test/views/workspace-view.test.ts` has a `FakeHost`, a `ResizeObserver` stand-in, and `resize()`. jsdom has no `ResizeObserver`, and the plugin tests stub it too.
- Native smoke: `yarn test:native` drives the real workspace, issue tabs, narrow pane and close command. It collapses Obsidian's sidebars first because the 1024 px sandbox window would otherwise make the pane narrow.
